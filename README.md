# Обзорник казино — движок

Статический генератор под ТЗ обзорников. Ноль зависимостей: в `package.json`
пустые `dependencies` и `devDependencies`, в проекте нет `node_modules`.

```
node build.js                 сборка в dist/
node build.js --lint-only     только проверка, без записи файлов
node build.js --stage=content ужесточить правила контента до ошибок
node serve.js                 посмотреть dist/ на localhost:4173 (с работающими 301)
```

## Что уже работает

ГЕО — Германия, тёмная тема, весь контент на немецком. Собирается 66 страниц и
233 редиректа из датасета на 18 брендов: 8 с эталона
`beste-online-casino-erfahrungen.de` (все без немецкой лицензии) и 10
GGL-лицензиатов из листа 03. Лист 03 требует разделять эти две группы, и без
обеих такого разделения не существует.

```
node build.js --stage=content   →  0 ошибок, 75 предупреждений
```

Вес: 1,1 МБ на 66 страниц, максимум 46 КБ на страницу при бюджете 300 КБ.
CSS 16,5 КБ, JS 13,6 КБ, зависимостей ноль.

### Волна публикации

`site.build.includeTerms` ограничивает выкладку 14 листингами, у которых есть
написанный текст. Остальные термы страниц не получают и отдают 301 на свой хаб —
битых ссылок не возникает. Лист 08 запрещает выкладывать «страницы без содержания
на потом», лист 05 советует идти волнами. Убрать список — соберутся все 47 листингов.

### Как решается уникальность

Лист 09 требует 40%+ различий между соседними листингами. Механизм:

- `data/content/de/payment-methods.json` — свойства каждого метода: лимиты, сроки,
  комиссии, работает ли на вывод, кому подходит, типичная ошибка
- `data/content/de/bonus-types.json` — то же по типам бонусов
- `data/content/de/categories.json` — по общим категориям
- расчётные секции из данных: у скольких брендов метод доступен на вывод, требуемый
  оборот по каждому офферу, разбивка листинга по лицензии

Плюс движок сам находит термы с одинаковым составом брендов и предлагает объединить
их через `aliasOf` — это прямая рекомендация листа 05.

### Правила честности, зашитые в движок

- Поле, не подтверждённое первоисточником, стоит `null`, а не правдоподобное число.
  В таблице на его месте «noch nicht geprüft».
- `payout.provisional: true` → критерий «Выплаты» (25% веса) **исключается** из
  расчёта, а не получает ноль. Ноль означал бы «платит медленно» — утверждение,
  которого мы не проверяли. Оценка считается по оставшимся 75%, и это видно на
  странице.
- Пока замеров нет, description берётся из отдельного варианта шаблона: иначе в
  выдачу попадает «0 Auszahlungen gemessen».
- Каждый бренд несёт `dataNotes.sources` и `dataNotes.unverified` — список того,
  что ещё предстоит сверить.

изображений и партнёрских ссылок уже боевые.

## Главный принцип

Бренд заводится **один раз** в `data/brands.json`. Дальше он попадает во все
подходящие листинги сам — по правилам `match` из `data/taxonomies.json`.
Списков брендов для листингов не существует как данных: они вычисляются.

```json
{ "slug": "paypal-casino", "match": { "payments": { "has": "paypal" } } }
```

Практическое следствие: чтобы убрать оператора со всего сайта, достаточно
сменить ему `status`. Чтобы обновить бонус на сорока страницах — поправить одно
поле. Это требование листа 05 («один источник данных»).

## Оценки не проставляются руками

`score.total` нигде не хранится. Он вычисляется из `data/criteria.json` при
каждой сборке, а попытка записать готовую оценку в данные ловится линтером.
Лист 05 называет оценку без основания риском ручных санкций, лист 04 разрешает
`AggregateRating` только при опубликованной методике — поэтому страница
`/how-we-test/` генерируется из того же файла, по которому считаются оценки.
Разойтись они не могут.

## Линтер

Валит сборку до того, как ошибку увидит заказчик. Правила взяты построчно из
листа 09 и блока «ЧЕГО НЕ ДЕЛАТЬ» листа 08:

- партнёрская ссылка без `rel="sponsored nofollow"`
- битая внутренняя ссылка, ссылка через 301 вместо канона
- страница без входящих ссылок; меньше трёх входящих
- листинг без настоящего `<table>` или без сортировки
- `<img>` без `width`/`height` или без `alt`
- отсутствие даты сверки в машиночитаемом виде
- Lorem Ipsum, счётчики «онлайн сейчас», таймеры срочности, форма с паролем
- `official` в title
- автор `admin` / `player` / `pin-admin`
- уникальность соседних листингов ниже 40% (шинглы по 5 слов)
- страница ответственной игры с офферами на ней

На этапе `harness` правила о качестве текста понижены до предупреждений:
контент ещё не написан, и сообщать о нём как об ошибке бессмысленно.
`--stage=content` включает их обратно.

## Смена ГЕО

Правится `data/site.json` и добавляется `data/locales/<код>.json` с тем же
набором ключей. Слаги хабов, служебных страниц, шаблоны заголовков, подписи
интерфейса, горячие линии — всё там. Код и шаблоны не трогаются.

Термы, специфичные для страны, помечены в `taxonomies.json`:

```json
{ "slug": "casinos-ohne-lizenz", "geo": ["DE"], "match": { ... } }
```

Терм чужого ГЕО не попадает в сборку ни страницей, ни редиректом.

## Короткие URL эталона

У эталона 111 из 256 адресов — короткие дубли вложенных страниц
(`/bitcoin/` дублирует `/casino-payment/bitcoin-casino/`). Мы отдаём с них 301
на канон: трафик по короткому запросу сохраняется, дубля нет.
Задаётся полем `short` у терма.

Синонимы (`crypto`/`cryptocurrency`, `eth`/`ethereum`, `xrp`/`ripple`,
`usdt`/`tether`) — поле `aliasOf`. Если канон сам не добрал порога из листа 05,
синоним ведёт туда же, куда ушёл канон: цепочек 301 → 301 не образуется.

## Структура

```
data/
  site.json            домен, ГЕО, тема, бюджеты, флаги compliance
  taxonomies.json      8 таксономий, ~140 термов, правила пересечения
  criteria.json        6 критериев с весами и правилами начисления
  brands.demo.json     демо-датасет, заменяется на реальный
  authors.json         редакция
  locales/en.json      всё, что зависит от языка
lib/                   генератор
templates/             стенд, заменяется после согласования дизайна
assets/js/             сортировка и фильтры
reports/               url-map.csv и lint.txt, пересобираются каждый раз
dist/                  результат
```
